Hybrid to Native

A workspace and process for building one app as two native apps, where AI agents build every feature on both platforms at the same time from one spec. Start from an existing React Native or Expo app, or from the product docs and designs of a new one.

iOS · Swift 6 + SwiftUI    Android · Kotlin + Compose    gate

Who's reading?

Pick your role. The page opens with the view for that role, and you can switch at any time from the bar at the top.

Analysis comes first

Nothing reaches the development team until the analysis handoff is accepted. That means a feature catalog covering every screen, the list of data the app stores on the device and how it will be migrated, the native replacement for every risky library, and ranked risks with owners. Specs are written from that evidence, and only approved specs get built.

For a new app the gate is the product handoff: every journey mapped to features with cited sources, the backend and design decisions made, a tracking plan, quality targets, and the store identity fixed.

Your view · Analysts

Turn the hybrid app into evidence

You read the React Native code (never change it), map what exists, and hand the team a reviewed analysis. Every claim cites a file and line. Anything that looks like a bug goes to open questions instead of being copied.

Shown by default because analysis comes first. Pick another role above to switch.

Steps

  1. Start with /kickoffIn a new session opened at the app's workspace. It checks the setup, asks which folder is the React Native app when the repo also holds a backend or web app, and fills PROJECT.md with you.
  2. Pin what users actually runThe production commit, plus the latest OTA update if expo-updates is used. Record the SHA.
  3. Scan the apprn-inventory maps routes, dependencies, stored data, API calls, analytics, test IDs, native modules and risks.
  4. Run /rn-analyzeWrites the analysis pack: architecture, feature catalog, integrations, data at rest, native code, risks.
  5. Run /plan-data-migrationHow the native apps read what the hybrid app left on the device, so nobody is logged out.
  6. Record the golden referenceMaestro flows and screenshots of the hybrid app. The same flows later run on both native apps.
  7. Propose waves and draft specs/spec-feature for each wave-1 feature, with open questions for the product owner.

Analysis handoff checklist

  • Every route and screen maps to one feature ID (or is marked out of scope)
  • Every value stored on the device has a decision: migrate, keep or drop
  • Every high-risk library has a native replacement or an open question
  • Risks ranked by impact and likelihood, each with an owner
  • Golden flows recorded for every critical journey
  • Orientation locks and iPad support noted for the Form factors sections
  • Product owner has reviewed the feature catalog and waves

New app: product definition instead of discovery

  1. Index the sourcesEvery PRD, brief, design file and piece of research gets a stable ID in analysis/sources/README.md. Specs cite those IDs.
  2. Draft the briefProblem, users, journeys, first-release scope and quality targets, each with a citation. Gaps become open questions, never invented requirements.
  3. Run workshops with Claude/define-product workshop <topic>: four questions at a time, decisions numbered, agent proposals marked as proposals. Notes count only once the product owner confirms them.
  4. Catalog, waves and decisionsFeature catalog with sources, design and API readiness; backend approach (existing API, contract-first with a mock, or BaaS) and design source as ADRs; tracking plan; store identity.
  5. Product handoffanalysis/HANDOFF.md, accepted by the product owner and both platform leads before any spec is built.
Your view · Engineers

Build approved specs on both platforms at once

You start from an approved spec, not from the hybrid code. The orchestrator writes the contract, the two platform agents build in parallel, and three reviewers check the result before you review and merge both PRs.

For each slice (the default)

  1. Once, at the start of Phase 2: /scaffold-nativeGenerates both projects from the kit templates (XcodeGen with a local Swift package; Gradle with convention plugins, Hilt, Navigation 3), with a sample feature, layout-matrix tests and CI, then builds and runs both.
  2. Pick a slice that ends in something tappableThe first one is always launch → login → main screen. Features in dependency order, in specs/slices/.
  3. Run /implement-slice <SLICE-ID>Contracts for the whole slice in one batch and one approval, then one iOS and one Android session build it feature by feature.
  4. Tap it earlyThe app runs on simulator and emulator as soon as it builds, before any review. Contract problems are logged and resolved once for both platforms.
  5. One review passParity plus iOS and Android quality reviews for the whole slice. Wording-only spec fixes are acknowledged in one command.
  6. Merge both PRs togetherTitled [SLICE-01] <demo goal>, each linking the other. Risky features (data migration, payments, auth) use /implement-feature instead.

Done means

  • Build, lint and tests green on both platforms
  • Every acceptance criterion has a test on both platforms, carrying its AC ID
  • Every screen renders correctly at any size and orientation, and the layout-matrix snapshots exist
  • Shared names match the contract exactly
  • Parity review PASS; quality reviews without blockers
  • Both PRs merged together; spec status set to implemented

Platform skills

26 third-party skills, pinned to exact commits. The iOS agents load the SwiftUI skill. The Android reviewer loads Compose performance and security skills. When a skill disagrees with the kit, the spec, contract and guidelines win, and guideline 14 lists every known conflict.

The skills are committed with the workspace: nothing to download after cloning, and nothing changes on checkout. Updates are reviewed bumps. On Windows, turn on Developer Mode and clone with git clone -c core.symlinks=true …, so other agent tools find them in .agents/skills (guideline 14 has the fix for an existing clone).

Conventions

  • Feature AUTH-LOGIN, criterion AUTH-LOGIN-AC03, never renumbered
  • Branch feature/AUTH-LOGIN in both repos
  • Commits [AUTH-LOGIN] Add login view model
  • Never hand-edit generated code; change contracts/ and regenerate

Your view · Stakeholders

Decide at the gates, watch the risks

The native apps replace the hybrid app as an update to the same store listings. Users keep the app and their data. They should only notice that it's faster. Your decisions shape what gets rebuilt, in what order, and when it ships. For a new app, you also decide the first release’s scope, the backend approach, the design source and the store identity.

What you decide

WhenDecision
Phase 1 gateAccept the analysis: feature catalog, waves, scope cuts
Every featureApprove its spec; decide whether odd hybrid behaviour is kept or fixed
Phase 0 / ongoingArchitecture decisions that change scope, such as minimum OS or phone orientation
New app, Phase 0–1Backend approach, design source, bundle ID and stores, confirmed workshop decisions
Phase 5 gateRelease date, rollout pace, kill criteria

How progress is measured

  • Features verified out of total, per wave
  • Acceptance-criteria coverage on each platform
  • Platform lag: days between the two platforms merging a feature (target: zero)
  • Crash-free sessions, cold start and funnel conversion against the hybrid baseline

Main risks and how the process handles them

Users logged out or losing data after the updateEvery stored value is inventoried in discovery; a migrator reads the hybrid formats; tested on two upgrade tracks before release.
The two apps drift apartOne spec and contract per feature, tests tagged per criterion, a parity review, and both PRs merged together.
Analytics dashboards break at cut-overEvent names are copied verbatim from the hybrid app and compared between apps on the same flows.
Over-the-air updates stopThe last hybrid OTA is frozen before cut-over; remote kill switches are in place before launch.
Foldables and large screensiPhone Duo and Android 16 ignore orientation locks, so every screen must render at any size and orientation.
The hybrid app keeps changingIt's frozen to critical fixes during the rewrite, and each change is mirrored into its spec.
Your view · QA

Prove parity with checks, not opinions

One Maestro suite runs unchanged against the hybrid app, the iOS app and the Android app. You record it against the hybrid app first, then it becomes the gate for both native apps. For a new app, the flows are written from the specs’ e2e criteria and run on both native apps, and the analytics diff compares iOS with Android.

Four parity checks

CheckProves
AC traceabilityEvery criterion has a test on iOS, on Android, and in a shared flow when marked e2e
Shared e2e flowsThe same journey works on all three apps (selected by test ID only)
Analytics diffThe same journey sends the same events with the same properties
Visual comparisonEach state looks right on both platforms; native idioms may differ

Layout matrix, every screen

  • Compact portrait
  • Compact landscape
  • Expanded (iPad, iPhone Duo inner display, foldable or tablet)
  • iPad, if the hybrid app supports it today

P0 journeys also run on one large device per platform.

Upgrade test, two tracks

  1. Local, on every buildRebuild the production hybrid commit, create data, install the native build over it, check that everything is still there.
  2. Real path, before each betaThe store hybrid version, then update through TestFlight and Play internal testing on real devices.

Release

Phased release on the App Store, staged rollout on Play, same day. Kill criteria are written in advance. Pausing an iOS phased release only stops automatic updates, so remote kill switches are the real brake there.
